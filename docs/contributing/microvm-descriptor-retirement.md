# VM descriptor retirement

The original VM owner fences new starts before cleanup and joins its native child and file borrowers. Its private file owner calls the concrete close once. The shared Linux close operation checks the actual unfiltered, untraced locked thread; unknown execution profiles and already-closed objects do not prove retirement.

A genuine late Linux close error can retire that descriptor while retaining its first diagnostic. Cleanup may then finish without issuing another close against a reused descriptor number. Failed writes, syncs, unlinks and unknown native lifetimes remain failures. The original failed preparation cannot start again.

VM lease release records the actual retired handle separately from its diagnostic. Metadata files remain with their original constructor on unknown results. The real root API closes only after borrowers join and is retried directly; no root-close error implies success.

A destructive cleanup records completed data deletion before closing resources. A retry finishes that same closure without reopening or deleting a replacement path. A factory that already released its preparation cannot recover destructive ownership from a saved path.

The final native slot evidence endpoint runs only after its genuine positive child closure and before remaining lease/root ownership is released. Original close diagnostics remain available on the actual VM owner for the preparation outcome, even when a later cleanup acknowledgement becomes possible.
