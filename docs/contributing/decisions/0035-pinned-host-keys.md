# 0035 Saved hosts pin their host key on the command line

This record applies the rule of [0034](0034-ssh-options-on-the-command-line.md) to host keys. Task H3 of [the isolation plan](../isolation-plan.md) builds it ([isolation spec, 14.7.1](../isolation-spec.md#1471-the-pinned-host-key)).

## Context

The client runs the system `ssh` with a generated config that includes the user's own ([0003](0003-system-openssh.md)). So the user's config decides which host keys `ssh` accepts. Many configs accept any key: `StrictHostKeyChecking no`, `UserKnownHostsFile /dev/null`, or both, often in a `Host *` block or a `Match` block. Lima's own SSH config has both lines, and also `NoHostAuthenticationForLocalhost yes`. Other sources can pass a key too: a wildcard or `@cert-authority` line in the system's known hosts file, an SSHFP record in DNS, and a `KnownHostsCommand`.

A host key that changes without a reason means a machine in the middle, or another machine at the same address. With a config that accepts any key, the client would connect to it, run the bridge, and attach the user's terminal to whatever answers. Sandboxes raise the stakes. A host's identity decides which secrets, keys and grants it gets ([isolation spec, 14.8](../isolation-spec.md#148-tiers-and-grants)).

OpenSSH keeps the first value that it finds for each of these options, and reads the command line before any config file. `HostKeyAlias` names the entry that `ssh` looks up, whatever the target's address and port are. A file of known hosts for one host then holds that host's key alone.

## Options

1. Leave host keys to the user's config, as today.
2. Warn when the user's config accepts any key, and connect anyway.
3. Check the key in the client, with its own SSH code, and keep using the system `ssh` for the rest.
4. Pin each saved host's key in a file of its own, `known_hosts-<name>`, and put the options that check it on every `ssh` command line. For the first pin, match the user's known hosts files in the client.
5. As option 4, but let OpenSSH decide which key the user's own settings trust, on a connection that logs in to nothing.

## Decision

Option 5.

- **One file for each host.** `~/.config/simstim/ssh/known_hosts-<key>` (0600) holds the host's keys under the name `simstim-<name>`. It is the record. H4 copies its fingerprint into `tiers.toml`. `<key>` is the host's file key, which every file of the host's own uses: the name in lower case, cut to 32 characters and with no dot or dash at its end, a dash, and 32 hex characters (128 bits) of SHA-256 over the exact name. So two names that differ only in case never share a file, also on a disk that ignores case, and each gets a pin of its own: 128 bits leave no pair that a person can make to collide. The pin's first line names the exact host, and every read checks it: a file whose first line names another host, or none, is never used, replaced or removed. A name that ends with a dot or a space is refused, because Windows drops those from a file's name. The pin's lock, `<key>.lock`, is never removed, so every client locks one file, also while another forgets the host.
- **The options of every command.** When the file exists, every `ssh` command for the host has `-o HostKeyAlias=simstim-<name> -o UserKnownHostsFile=<the file> -o StrictHostKeyChecking=yes -o UpdateHostKeys=no -o GlobalKnownHostsFile=/dev/null -o VerifyHostKeyDNS=no -o NoHostAuthenticationForLocalhost=no -o CheckHostIP=no -o FingerprintHash=sha256 -o LogLevel=ERROR`. Where the local `ssh` knows them, it also has `-o KnownHostsCommand=none` (OpenSSH 8.5 and later) and `-o NoHostAuthenticationForProxyCommand=no` (in the `ssh` builds that have the option). The client asks `ssh -G` once whether it knows each option. Only `ssh`'s own "Bad configuration option" or "Unsupported option" says no. A timeout or another failure is an error: the command fails, and the client asks again next time. The last three options keep `ssh` from writing to the pin, and keep the changed-key message and its SHA256 fingerprint whatever the user's config says. `LogLevel=ERROR` also hides a host's banner, which could imitate that message.
- **Where the pin comes from.** `host add` first asks OpenSSH. A connection with the user's own known hosts settings, which forces only strict checking, no question, no login, no write to a file and a debug log, shows whether `ssh` trusts the key that the host shows: through a known hosts line, hashed or with a port wildcard, a `@cert-authority` line, a `KnownHostsCommand` or DNS. When it does, a second connection reads that key, and the client pins it. A key that the user's settings revoke is refused, and so is a key that they name with another key, unless `--host-key` names the key. A key to pin of another type than the one that the first connection saw is checked in the same way, on a connection of its own type, so a revoked key is never pinned beside a trusted one. With `--host-key SHA256:…`, the client pins only the key with that fingerprint. Otherwise it reads the key that the host shows. At a terminal, `ssh` shows the fingerprint and asks. With `--yes`, the client pins the key on first use and says how to check it. With input off and neither flag, `host add` fails with exit code 4. `host create lima` pins the new VM's key on first use. Every connection that asks or reads a key offers no key, no password and no agent, so it ends after the key exchange.
- **How the client reads the verdict.** `ssh` writes its log to a file of its own (`-E`), and the client reads only that file, so a `ProxyJump` hop's banner and log, which go to stderr, never count. A host's own text still reaches the file: `ssh` logs a certificate's key ID before its verdict, and a key ID can hold a line break and a line that looks like `ssh`'s. So the most severe verdict anywhere in the log wins: revoked or changed, then not known, then trusted. A host cannot stop `ssh` from writing its own failure lines, so its text can only make the answer stricter. A verdict also needs `ssh`'s own end: "trusted" needs the login and an `ssh` that ran the command, or whose last line is the host's refusal of the login, and "not known" needs "Host key verification failed." as the last line. A time limit, a log that cannot be read, a failure of `ssh`'s own such as a `KnownHostsCommand` that fails, or a log that names two different keys decide nothing: the client fails closed. Its errors say in fixed words what failed, and never quote what a host or a hop wrote, which could hold a false `Try:` line.
- **Every connection checks a pin.** A command that can log in builds its options from one snapshot of the pin, read under the pin's lock, so the check and the options never differ. With no pin and no stage, it refuses, saved host or not. The guided setup's check that `ssh` logs in stages the key that the user's settings trust, and logs in with it alone.
- **The pin follows the save.** `host add` keeps a new pin apart, in a staged file that its own connections check, until it saves the host. It then moves the pin into place under the pin's lock. A `host add` that fails leaves no pin. When another client saved the host with another pin meanwhile, it saves nothing, and fails with exit code 5. The save is one step: a failure leaves the host list and the pin as they were. The launcher's add-host wizard does the same, and shows a key that the user's settings do not name, and asks, since `ssh` cannot ask in the launcher.
- **A changed key is a refusal.** `ssh` then fails, and the client shows the message of spec 14.14 with both fingerprints, and exits with 5. Only `host rekey` replaces a pin: `host add` never does, whatever the host's target. `host rekey` reads the key again in the same way, shows the old and the new fingerprint, and asks for the host's typed name, or takes `--confirm <host>`.
- **Retire the host's masters.** A random 128-bit epoch folder holds each pin namespace's `nf-%C` sockets. A private index maps the exact host and canonical pin set to that folder. The index's host and pin labels hold 128 bits of SHA-256 and include the physical client config root. The labels and epoch tokens use 26 lower-case base32 characters. Publication holds the pin lock, so it cannot race with removal. Forget and rekey rename the epoch first, even when the pin or user SSH config cannot be read. An SSH operation paused during authentication cannot then bind or link a new socket at its old path. The client sends `ssh -O exit` to each concrete retired socket without a remote login, then removes it. A re-add allocates a fresh epoch. Other hosts and client roots keep their sockets. The final path is capped at 86 bytes, leaving 17 for OpenSSH's temporary bind suffix. A retained base is owned by this user with mode `0700`. Its fallback is `/tmp/cm-<uid in base36>`. When the base or index is unsafe, a command uses its own connection.
- **Operation-owned stages.** An add operation carries its stage identity through pin checks, connections and the final save. Its abort closes only that stage. A stopped or superseded operation fails closed. It never adopts or removes a newer stage. Hosts use a single locked read, change and atomic write of `hosts.toml`, after the per-host pin lock.
- **SSH exit state.** An early output close gets a bounded exit grace before the client kills a stalled SSH process. This keeps missing-helper and changed-key results accurate. Forwarded output is cleaned. `pull` runs SSH through a private child of the same client binary and records the actual exit state before Git reports its own result. A local lease bounds that child's SSH lifetime after unexpected client loss. No new runtime dependency or network listener is added.
- **Hosts saved before.** A saved host without a pin gets it at its next connection, once, before any `ssh` command logs in to it. When the user's settings trust its key, the client pins that key. Otherwise it pins on first use where the user's config takes a new key without a question, or for a machine that the client made. Otherwise `ssh` asks at a terminal, and without one the connection fails with exit code 4. A failure of the pin stops the connection, and so does a `hosts.toml` that cannot be read. A pin that the first version of H3 named `known_hosts-<name>` moves to its new name, under the lock, once.
- **Jump hosts follow the user's config.** Options on the command line do not reach the `ssh` of a `ProxyJump` hop. The session to the destination is end-to-end SSH with a pinned key, so a hop can neither read nor change it. The hop cannot choose the pin either, because its words never reach the log file that the client reads.

Option 1 leaves the hole open. Option 2 leaves it open for anyone who does not read the warning. Option 3 needs a second SSH stack, and the client would still run the system `ssh` with the user's config, which could accept another key. Option 4's matcher would drift from OpenSSH's: reviews found port wildcards, several relative files and large files where it differed. Option 5 uses only `ssh`'s own options and verdicts, wins over every config file, and a test of the arguments reads it.

## Consequences

- Good, because no line of a config file, an `Include` or a `Match` block can make the client accept another key for a saved host.
- Good, because the first pin trusts exactly what the user's own `ssh` trusts, and a test against a real sshd checks it.
- Good, because a changed key stops every command with one message, which names both fingerprints and the way out.
- Good, because the pin is a plain known hosts file, which the user can read, and which `ssh-keygen -lf` prints.
- Good, because `ps` shows the options, as it shows those of 0034.
- Bad, because `host add` makes two connections more, each of which logs in to nothing.
- Bad, because a reinstalled host needs `host rekey` and a typed name before the client connects again.
- Bad, because `host add` with input off fails for a host whose key the user's settings do not trust, until the script passes `--host-key` or `--yes`. A host saved before pins fails the same way without a terminal, until `host rekey` pins it.
- Bad, because a host whose key comes only from a certificate authority gets its own key pinned. A rotated host key then needs `host rekey`, even when the authority signed it.
- Bad, because a file of a host's own has a name that is harder to read than the host's name, such as `known_hosts-box-26f8567f2569182294c3fa5b9f9cb227`.
- Bad, because the trust check stops at a log that names two keys, or a failure line of the host's own, even where `ssh` itself would go on. The user must fix the SSH config or the host first.
