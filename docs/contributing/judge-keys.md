# Trusted classifier credentials

A classifier key has a closed trusted use in the existing credential registry.
Its role names the model, endpoint and HTTPS header binding. The classifier
reference grants no guest environment entry, sentinel or network permission.
An ordinary guest use of the same name needs its own separate approval. Both
uses retain the same fetched value in the same registry.

The original New, cold Resume or explicit arm request retains its local
settings descriptor, accepted connection, host identity, wall and ceiling.
Every value check uses that same source. A missing configured key fails closed.
An explicitly configured anonymous local model uses no key command.

Normal name, kind, host and tier checks run before fetching. Shared host
confirmation has a separate scope from the guest's question. An own-tier key
on a process wall also needs a separate request-local risk answer. That answer
defaults to refusal and grants no guest exposure. Host floors remain separate.

Cold Resume requires the existing original native preparation before any
credential command. A warm Resume fetches no classifier credential. The final
physical request checks the retained preparation without issuing another RPC.
The supervisor still checks its actual native owner and generation.

Only the original fixed-payload model caller can use the private header
injector. It checks the current source, model, endpoint and trusted role.
Guest value rotation leaves the trusted role unarmed until its separate
protected arm operation completes. A trusted arm cannot rotate a separately
authorised guest value on its own.

Policy replacement alone does not fetch or arm credentials. A changed key or
endpoint remains unavailable until a new explicit authorised lifecycle installs
its binding. Source replacement and shutdown cancel and join physical work.
The request keeps its descriptor while a value command is still busy.

Manifests and acknowledgements retain role metadata only. Values remain in
protected memory and do not enter policy files, audit, native metadata or
saved images. The compatibility feature is advertised only after every real
client, host, supervisor and Egress route supports this lifecycle.

Attach and reconnect use the same original arm request before the terminal
pump starts. Ordinary bound names come from the laptop's original creation
record and allowed set. Host display rows cannot select names. Exposed values
and SSH keys do not enter this arm route.

A fresh protected cohort checks ordinary bound readiness. The trusted judge
uses an additional names-only readiness query for the exact original role
and generation. Egress compares the complete role tuple before returning the
observation. Missing or malformed observations permit no skip or blind refetch.
Already armed roles fetch nothing and ask no new delivery question.

When either half of a separately authorised shared name needs a value, both
roles pass their own current checks before one command runs. Successful reads
stay in the same request through later failures and retries. The final request
compares the original source, cohort and generation again. A metadata DTO or
an earlier acknowledgement cannot construct this operation.

When the exact requested role matches current policy, an absent or older
stored tuple is an unarmed observation. It grants no fetch permission. The
new original request still completes every independent delivery check before
it can install that current role.

A completed arm writes a version 2 delivery receipt through the existing
native file compare and swap. The original request retains its exact writer
identity, complete-write evidence and correlated acknowledgement. Guest and
trusted arm deltas are separate. The guest allowance stays unchanged.
Read-only readiness writes no receipt. The private wire hash and real values
never enter the receipt. Older readers preserve an unselected future receipt
and refuse to use it for a selected operation.
